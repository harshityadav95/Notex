## Step 1 - Understand the problem and establish design scope

<section class="chapter-video" aria-label="Video for Step 1 - Understand the problem and establish design scope"><span class="video-play" aria-hidden="true">▷</span><div><span class="eyebrow">SECTION VIDEO</span><strong>Step 1 - Understand the problem and establish design scope</strong><p>Video coming soon. Start with the reading below.</p></div><span class="video-coming">COMING SOON</span></section>

<p>It is vital to agree on the type of chat app to design. In the marketplace, there are one-on-one chat apps like Facebook Messenger, WeChat, and WhatsApp, office chat apps that focus on group chat like Slack, or game chat apps, like Discord, that focus on large group interaction and low voice chat latency.</p>
<p>The first set of clarification questions should nail down what the interviewer has in mind exactly when she asks you to design a chat system. At the very least, figure out if you should focus on a one-on-one chat or group chat app. Some questions you might ask are as follows:</p>
<p><strong>Candidate</strong>: What kind of chat app shall we design? 1 on 1 or group based? <strong>Interviewer</strong>: It should support both 1 on 1 and group chat.</p>
<p><strong>Candidate</strong>: Is this a mobile app? Or a web app? Or both? <strong>Interviewer</strong>: Both.</p>
<p><strong>Candidate</strong>: What is the scale of this app? A startup app or massive scale? <strong>Interviewer</strong>: It should support 50 million daily active users (DAU).</p>
<p><strong>Candidate</strong>: For group chat, what is the group member limit? <strong>Interviewer</strong>: A maximum of 100 people</p>
<p><strong>Candidate</strong>: What features are important for the chat app? Can it support attachment? <strong>Interviewer</strong>: 1 on 1 chat, group chat, online indicator. The system only supports text messages.</p>
<p><strong>Candidate</strong>: Is there a message size limit? <strong>Interviewer</strong>: Yes, text length should be less than 100,000 characters long.</p>
<p><strong>Candidate</strong>: Is end-to-end encryption required? <strong>Interviewer</strong>: Not required for now but we will discuss that if time allows.</p>
<p><strong>Candidate</strong>: How long shall we store the chat history?  <strong>Interviewer</strong>: Forever.</p>
<p>In the chapter, we focus on designing a chat app like Facebook messenger, with an emphasis on the following features:</p>
<ul><li>A one-on-one chat with low delivery latency</li><li>Small group chat (max of 100 people)</li><li>Online presence</li><li>Multiple device support. The same account can be logged in to multiple accounts at the same time.</li><li>Push notifications</li></ul>
<p>It is also important to agree on the design scale. We will design a system that supports 50 million DAU.</p>

## Step 2 - Propose high-level design and get buy-in

<section class="chapter-video" aria-label="Video for Step 2 - Propose high-level design and get buy-in"><span class="video-play" aria-hidden="true">▷</span><div><span class="eyebrow">SECTION VIDEO</span><strong>Step 2 - Propose high-level design and get buy-in</strong><p>Video coming soon. Start with the reading below.</p></div><span class="video-coming">COMING SOON</span></section>

<p>To develop a high-quality design, we should have a basic knowledge of how clients and servers communicate. In a chat system, clients can be either mobile applications or web applications. Clients do not communicate directly with each other. Instead, each client connects to a chat service, which supports all the features mentioned above. Let us focus on fundamental operations. The chat service must support the following functions:</p>
<ul><li>Receive messages from other clients.</li><li>Find the right recipients for each message and relay the message to the recipients.</li><li>If a recipient is not online, hold the messages for that recipient on the server until she is online.</li></ul>
<p>Figure 12-2 shows the relationships between clients (sender and receiver) and the chat service.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-146.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 146" height="204" loading="lazy" src="../../assets/system-design/figure-146.jpeg" width="940"/></a></figure>
<p>When a client intends to start a chat, it connects the chats service using one or more network protocols. For a chat service, the choice of network protocols is important. Let us discuss this with the interviewer.</p>
<p>Requests are initiated by the client for most client/server applications. This is also true for the sender side of a chat application. In Figure 12-2, when the sender sends a message to the receiver via the chat service, it uses the time-tested HTTP protocol, which is the most common web protocol. In this scenario, the client opens a HTTP connection with the chat service and sends the message, informing the service to send the message to the receiver. The keep-alive is efficient for this because the keep-alive header allows a client to maintain a persistent connection with the chat service. It also reduces the number of TCP handshakes. HTTP is a fine option on the sender side, and many popular chat applications such as Facebook <a href="study:system-design/lessons/12-13-step-4-wrap-up/#reference-12-1">[1]</a> used HTTP initially to send messages.</p>
<p>However, the receiver side is a bit more complicated. Since HTTP is client-initiated, it is not trivial to send messages from the server. Over the years, many techniques are used to simulate a server-initiated connection: polling, long polling, and WebSocket. Those are important techniques widely used in system design interviews so let us examine each of them.</p>

## Long polling

<section class="chapter-video" aria-label="Video for Long polling"><span class="video-play" aria-hidden="true">▷</span><div><span class="eyebrow">SECTION VIDEO</span><strong>Long polling</strong><p>Video coming soon. <p>Because polling could be inefficient, the next progression is long polling (Figure 12-4).</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-148.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 148" height="886" loading="lazy" src="../../assets/system-design/figure-148.jpeg" width="940"/></a></figure>
<p>In long polling, a client holds the connection open until there are actually new messages available or a timeout threshold has been reached. Once the client receives new messages, it immediately sends another request to the server, restarting the process. Long polling has a few drawbacks:</p>
<ul><li>Sender and receiver may not connect to the same chat server. HTTP based servers are usually stateless. If you use round robin for load balancing, the server that receives the message might not have a long-polling connection with the client who receives the message.</li><li>A server has no good way to tell if a client is disconnected.</li><li>It is inefficient. If a user does not chat much, long polling still makes periodic connections after timeouts.</li></ul>

## WebSocket

<section class="chapter-video" aria-label="Video for WebSocket"><span class="video-play" aria-hidden="true">▷</span><div><span class="eyebrow">SECTION VIDEO</span><strong>WebSocket</strong><p>Video coming soon. <p>WebSocket is the most common solution for sending asynchronous updates from server to client. Figure 12-5 shows how it works.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-149.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 149" height="615" loading="lazy" src="../../assets/system-design/figure-149.jpeg" width="940"/></a></figure>
<p>WebSocket connection is initiated by the client. It is bi-directional and persistent. It starts its life as a HTTP connection and could be “upgraded” via some well-defined handshake to a WebSocket connection. Through this persistent connection, a server could send updates to a client. WebSocket connections generally work even if a firewall is in place. This is because they use port 80 or 443 which are also used by HTTP/HTTPS connections.</p>
<p>Earlier we said that on the sender side HTTP is a fine protocol to use, but since WebSocket is bidirectional, there is no strong technical reason not to use it also for sending. Figure 12-6 shows how WebSockets (ws) is used for both sender and receiver sides.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-150.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 150" height="642" loading="lazy" src="../../assets/system-design/figure-150.jpeg" width="981"/></a></figure>
<p>By using WebSocket for both sending and receiving, it simplifies the design and makes implementation on both client and server more straightforward. Since WebSocket connections are persistent, efficient connection management is critical on the server-side.</p>

## High-level design

<section class="chapter-video" aria-label="Video for High-level design"><span class="video-play" aria-hidden="true">▷</span><div><span class="eyebrow">SECTION VIDEO</span><strong>High-level design</strong><p>Video coming soon. Start with the reading below.</p></div><span class="video-coming">COMING SOON</span></section>

<p>Just now we mentioned that WebSocket was chosen as the main communication protocol between the client and server for its bidirectional communication, it is important to note that everything else does not have to be WebSocket. In fact, most features (sign up, login, user profile, etc) of a chat application could use the traditional request/response method over HTTP. Let us drill in a bit and look at the high-level components of the system.</p>
<p>As shown in Figure 12-7, the chat system is broken down into three major categories: stateless services, stateful services, and third-party integration.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-151.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 151" height="997" loading="lazy" src="../../assets/system-design/figure-151.jpeg" width="750"/></a></figure>
<p><strong>Stateless Services</strong> Stateless services are traditional public-facing request/response services, used to manage the login, signup, user profile, etc. These are common features among many websites and apps.</p>
<p>Stateless services sit behind a load balancer whose job is to route requests to the correct services based on the request paths. These services can be monolithic or individual microservices. We do not need to build many of these stateless services by ourselves as there are services in the market that can be integrated easily. The one service that we will discuss more in deep dive is the service discovery. Its primary job is to give the client a list of DNS host names of chat servers that the client could connect to.</p>

<p><strong>Stateful Service</strong> The only stateful service is the chat service. The service is stateful because each client maintains a persistent network connection to a chat server. In this service, a client normally does not switch to another chat server as long as the server is still available. The service discovery coordinates closely with the chat service to avoid server overloading. We will go into detail in deep dive.</p>
<p><strong>Third-party integration</strong> For a chat app, push notification is the most important third-party integration. It is a way to inform users when new messages have arrived, even when the app is not running. Proper integration of push notification is crucial. Refer to Chapter 10 Design a notification system for more information.</p>
<p><strong>Scalability</strong> On a small scale, all services listed above could fit in one server. Even at the scale we design for, it is in theory possible to fit all user connections in one modern cloud server. The number of concurrent connections that a server can handle will most likely be the limiting factor. In our scenario, at 1M concurrent users, assuming each user connection needs 10K of memory on the server (this is a very rough figure and very dependent on the language choice), it only needs about 10GB of memory to hold all the connections on one box.</p>
<p>If we propose a design where everything fits in one server, this may raise a big red flag in the interviewer’s mind. No technologist would design such a scale in a single server. Single server design is a deal breaker due to many factors. The single point of failure is the biggest among them.</p>
<p>However, it is perfectly fine to start with a single server design. Just make sure the interviewer knows this is a starting point. Putting everything we mentioned together, Figure 12-8 shows the adjusted high-level design.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-152.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 152" height="1007" loading="lazy" src="../../assets/system-design/figure-152.jpeg" width="885"/></a></figure>
<p>In Figure 12-8, the client maintains a persistent WebSocket connection to a chat server for real-time messaging.</p>
<ul><li>Chat servers facilitate message sending/receiving.</li><li>Presence servers manage online/offline status.</li><li>API servers handle everything including user login, signup, change profile, etc.</li><li>Notification servers send push notifications.</li><li>Finally, the key-value store is used to store chat history. When an offline user comes online, she will see all her previous chat history.</li></ul>
<p><strong>Storage</strong> At this point, we have servers ready, services up running and third-party integrations complete. Deep down the technical stack is the data layer. Data layer usually requires some effort to get it correct. An important decision we must make is to decide on the right type of database to use: relational databases or NoSQL databases? To make an informed decision, we will examine the data types and read/write patterns.</p>

<p>Two types of data exist in a typical chat system. The first is generic data, such as user profile, setting, user friends list. These data are stored in robust and reliable relational databases. Replication and sharding are common techniques to satisfy availability and scalability requirements.</p>
<p>The second is unique to chat systems: chat history data. It is important to understand the read/write pattern.</p>
<ul><li>The amount of data is enormous for chat systems. A previous study <a href="study:system-design/lessons/12-13-step-4-wrap-up/#reference-12-2">[2]</a> reveals that Facebook messenger and Whatsapp process 60 billion messages a day.</li><li>Only recent chats are accessed frequently. Users do not usually look up for old chats.</li><li>Although very recent chat history is viewed in most cases, users might use features that require random access of data, such as search, view your mentions, jump to specific messages, etc. These cases should be supported by the data access layer.</li><li>The read to write ratio is about 1:1 for 1 on 1 chat apps.</li></ul>
<p>Selecting the correct storage system that supports all of our use cases is crucial. We recommend key-value stores for the following reasons:</p>
<ul><li>Key-value stores allow easy horizontal scaling.</li><li>Key-value stores provide very low latency to access data.</li><li>Relational databases do not handle long tail <a href="study:system-design/lessons/12-13-step-4-wrap-up/#reference-12-3">[3]</a> of data well. When the indexes grow large, random access is expensive.</li><li>Key-value stores are adopted by other proven reliable chat applications. For example, both Facebook messenger and Discord use key-value stores. Facebook messenger uses HBase <a href="study:system-design/lessons/12-13-step-4-wrap-up/#reference-12-4">[4]</a>, and Discord uses Cassandra <a href="study:system-design/lessons/12-13-step-4-wrap-up/#reference-12-5">[5]</a>.</li></ul>

## Data models

<section class="chapter-video" aria-label="Video for Data models"><span class="video-play" aria-hidden="true">▷</span><div><span class="eyebrow">SECTION VIDEO</span><strong>Data models</strong><p>Video coming soon. <p>Just now, we talked about using key-value stores as our storage layer. The most important data is message data. Let us take a close look.</p>
<p><strong>Message table for 1 on 1 chat</strong> Figure 12-9 shows the message table for 1 on 1 chat. The primary key is <em>message_id</em>, which helps to decide message sequence. We cannot rely on <em>created_at</em> to decide the message sequence because two messages can be created at the same time.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-153.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 153" height="875" loading="lazy" src="../../assets/system-design/figure-153.jpeg" width="930"/></a></figure>
<p><strong>Message table for group chat</strong> Figure 12-10 shows the message table for group chat. The composite primary key is <em>(channel_id, message_id).</em> Channel and group represent the same meaning here. <em>channel_id</em> is the partition key because all queries in a group chat operate in a channel.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-154.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 154" height="783" loading="lazy" src="../../assets/system-design/figure-154.jpeg" width="820"/></a></figure>
<p><strong>Message ID</strong></p>
<p>How to generate <em>message_id</em> is an interesting topic worth exploring. <em>Message_id</em> carries the responsibility of ensuring the order of messages. To ascertain the order of messages, <em>message_id</em> must satisfy the following two requirements:</p>
<ul><li>IDs must be unique.</li><li>IDs should be sortable by time, meaning new rows have higher IDs than old ones.</li></ul>
<p>How can we achieve those two guarantees? The first idea that comes to mind is the “<em>auto_increment</em>” keyword in MySql. However, NoSQL databases usually do not provide such a feature.</p>
<p>The second approach is to use a global 64-bit sequence number generator like Snowflake <a href="study:system-design/lessons/12-13-step-4-wrap-up/#reference-12-6">[6]</a>. This is discussed in “Chapter 7: Design a unique ID generator in a distributed system”.</p>
<p>The final approach is to use local sequence number generator. Local means IDs are only unique within a group. The reason why local IDs work is that maintaining message sequence within one-on-one channel or a group channel is sufficient. This approach is easier to implement in comparison to the global ID implementation.</p>

<p>It is interesting to understand the end-to-end flow of a chat system. In this section, we will explore 1 on 1 chat flow, message synchronization across multiple devices and group chat flow.</p>

<p><strong>1 on 1 chat flow</strong> Figure 12-12 explains what happens when User A sends a message to User B.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-156.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 156" height="842" loading="lazy" src="../../assets/system-design/figure-156.jpeg" width="755"/></a></figure>

<p><strong>Message synchronization across multiple devices</strong> Many users have multiple devices. We will explain how to sync messages across multiple devices. Figure 12-13 shows an example of message synchronization.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-157.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 157" height="924" loading="lazy" src="../../assets/system-design/figure-157.jpeg" width="1218"/></a></figure>
<p>In Figure 12-13, user A has two devices: a phone and a laptop. When User A logs in to the chat app with her phone, it establishes a WebSocket connection with Chat server 1. Similarly, there is a connection between the laptop and Chat server 1.</p>
<p>Each device maintains a variable called <em>cur_max_message_id</em>, which keeps track of the latest message ID on the device. Messages that satisfy the following two conditions are considered as news messages:</p>
<ul><li>The recipient ID is equal to the currently logged-in user ID.</li><li>Message ID in the key-value store is larger than <em>cur_max_message_id</em> .</li></ul>
<p>With distinct <em>cur_max_message_id</em> on each device, message synchronization is easy as each device can get new messages from the KV store.</p>
<p><strong>Small group chat flow</strong> In comparison to the one-on-one chat, the logic of group chat is more complicated. Figures 12-14 and 12-15 explain the flow.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-158.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 158" height="924" loading="lazy" src="../../assets/system-design/figure-158.jpeg" width="992"/></a></figure>
<p>Figure 12-14 explains what happens when User A sends a message in a group chat. Assume there are 3 members in the group (User A, User B and user C). First, the message from User A is copied to each group member’s message sync queue: one for User B and the second for User C. You can think of the message sync queue as an inbox for a recipient. This design choice is good for small group chat because:</p>
<ul><li>it simplifies message sync flow as each client only needs to check its own inbox to get new messages.</li><li>when the group number is small, storing a copy in each recipient’s inbox is not too expensive.</li></ul>
<p>WeChat uses a similar approach, and it limits a group to 500 members <a href="study:system-design/lessons/12-13-step-4-wrap-up/#reference-12-8">[8]</a>. However, for groups with a lot of users, storing a message copy for each member is not acceptable.</p>
<p>On the recipient side, a recipient can receive messages from multiple users. Each recipient has an inbox (message sync queue) which contains messages from different senders. Figure 12-15 illustrates the design.</p>

## Online presence

<section class="chapter-video" aria-label="Video for Online presence"><span class="video-play" aria-hidden="true">▷</span><div><span class="eyebrow">SECTION VIDEO</span><strong>Online presence</strong><p>Video coming soon. Start with the reading below.</p></div><span class="video-coming">COMING SOON</span></section>

<p>An online presence indicator is an essential feature of many chat applications. Usually, you can see a green dot next to a user’s profile picture or username. This section explains what happens behind the scenes.</p>
<p>In the high-level design, presence servers are responsible for managing online status and communicating with clients through WebSocket. There are a few flows that will trigger online status change. Let us examine each of them.</p>
<p><strong>User login</strong> The user login flow is explained in the “Service Discovery” section. After a WebSocket connection is built between the client and the real-time service, user A’s online status and <em>last_active_at</em> timestamp are saved in the KV store. Presence indicator shows the user is online after she logs in.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-160.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 160" height="344" loading="lazy" src="../../assets/system-design/figure-160.jpeg" width="1104"/></a></figure>
<p><strong>User logout</strong> When a user logs out, it goes through the user logout flow as shown in Figure 12-17. The online status is changed to offline in the KV store. The presence indicator shows a user is offline.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-161.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 161" height="324" loading="lazy" src="../../assets/system-design/figure-161.jpeg" width="1344"/></a></figure>
<p><strong>User disconnection</strong> We all wish our internet connection is consistent and reliable. However, that is not always the case; thus, we must address this issue in our design. When a user disconnects from the internet, the persistent connection between the client and server is lost. A naive way to handle user disconnection is to mark the user as offline and change the status to online when the connection re-establishes. However, this approach has a major flaw. It is common for users to disconnect and reconnect to the internet frequently in a short time. For example, network connections can be on and off while a user goes through a tunnel. Updating online status on every disconnect/reconnect would make the presence indicator change too often, resulting in poor user experience.</p>
<p>We introduce a heartbeat mechanism to solve this problem. Periodically, an online client sends a heartbeat event to presence servers. If presence servers receive a heartbeat event within a certain time, say x seconds from the client, a user is considered as online. Otherwise, it is offline.</p>
<p>In Figure 12-18, the client sends a heartbeat event to the server every 5 seconds. After sending 3 heartbeat events, the client is disconnected and does not reconnect within x = 30 seconds (This number is arbitrarily chosen to demonstrate the logic). The online status is changed to offline.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-162.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 162" height="725" loading="lazy" src="../../assets/system-design/figure-162.jpeg" width="856"/></a></figure>
<p><strong>Online status fanout</strong> How do user A’s friends know about the status changes? Figure 12-19 explains how it works. Presence servers use a publish-subscribe model, in which each friend pair maintains a channel. When User A’s online status changes, it publishes the event to three channels, channel A-B, A-C, and A-D. Those three channels are subscribed by User B, C, and D, respectively. Thus, it is easy for friends to get online status updates. The communication between clients and servers is through real-time WebSocket.</p>
<figure class="source-figure"><a aria-label="Open diagram at full resolution" href="../../assets/system-design/figure-163.jpeg" rel="noopener" target="_blank"><img alt="Design a chat system — original diagram 163" height="487" loading="lazy" src="../../assets/system-design/figure-163.jpeg" width="940"/></a></figure>
<p>The above design is effective for a small user group. For instance, WeChat uses a similar approach because its user group is capped to 500. For larger groups, informing all members about online status is expensive and time consuming. Assume a group has 100,000 members. Each status change will generate 100,000 events. To solve the performance bottleneck, a possible solution is to fetch online status only when a user enters a group or manually refreshes the friend list.</p>
